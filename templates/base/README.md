# __APP_SLUG__

A full-stack TypeScript monorepo generated by **create-pimasi-app**. It ships with auth, a database-backed API, and a web app already wired together.

> This README is a guide, not gospel — if in doubt, _always ask your teammates_.

## Architecture

This is a **Turborepo + npm workspaces** monorepo. Three workspaces divide the stack cleanly:

- **Web app** (`apps/web/`) — a browser SPA built with either **TanStack Router + Vite** or **Next.js (App Router)**, depending on how the project was generated. Either way it is a pure client of the Express API, styled with Tailwind 4. UI primitives (`Button`, `Input`, `Spinner`) live in the app's own `components/ui/` (imported as `@/components/ui/*`), themed by the design system chosen at scaffold time — shadcn/ui or bespoke tokens — under the same component API either way. When Cordova is enabled, the same web app packages into Android/iOS via the shell in `apps/web/cordova/`.
- **Server** (`apps/server/`) — Express 5 API on **MongoDB or Postgres**, with **optional Firebase** auth alongside email/password. Four server features are **optional, chosen at scaffold time or added later** (`npx pimasi add <feature>` — it reads `pimasi.json`), and present only if selected: **background workers** (BullMQ queues + a separate `workers` process), a Redis-backed **`$cache` service**, Redis-backed **rate limiting** on the auth routes, and **WebSockets** (realtime push over `$bus`, the Redis-backed messaging seam — ephemeral broadcast channels by default, durable channels with consumer groups via `$bus.channel(name, { durable: true })`; when selected, mount the shipped `WebSocketProvider` in your app shell and subscribe with `useWSEvent`). The database sits behind a repository interface (`apps/server/src/models/*.ts`), so the auth handlers never see the driver.
- **Shared lib** (`apps/shared/lib/`) — `@pimasi/lib`: the runtime **schemas** (request/response shapes) and **values** (enums like `UserRoles`) shared by web and server.

External utilities come from the published **`@pimasi/utils`** package (HTTP client, JSON-schema, logger, typed errors, helpers) — never rename it.


## Dev environment

> Docker & Docker Compose are **required**; Node.js on the host is only for type-checking, formatting, and editor tooling.

The dev environment is **100% dockerised** and must be treated as such: server, web, database, and Redis (when selected) all run in containers. The **only host-side commands** are type-checking and the formatter. `make` targets are the interface; prefer `make` over `npm run`.

```sh
make setup       # copy .env.example to .env if missing + npm install (editor tooling)
make dev         # docker compose up --build --watch (full stack, live reload)
make dev-clean   # reset volumes, then a fresh dev stack
make test        # run every test inside the server container
make type-check  # host-side, static
make format      # host-side, prettier
make update-deps # bump every dependency to latest (npm-check-updates) + install
```

After `make setup`, fill in real `.env` values (ask teammates for secrets). On the Mongo variant, extra `mongo-seed` targets exist for seeding the database.

Commit `package-lock.json` after setup and dependency changes. The Dockerfiles use `npm ci`, which requires a lockfile matching the workspace manifests.

> The Docker dev stack covers the **browser** app only. Packaging the SPA as an Android/iOS app is a separate, **host-side** flow — see [Mobile builds (Cordova)](#mobile-builds-cordova).

## Build & commands

- The monorepo uses **npm workspaces + Turborepo** for task orchestration; `make` targets wrap the day-to-day commands.
- **Builds and tests run through Docker/make**: `make dev` builds the images, `make test` runs the suite inside the server container.
- The server image transpiles `apps/shared/lib/` and `apps/server/` in one TypeScript project-reference build.
- The **host-side exceptions** are `npm run type-check` (`make type-check`) and prettier (`make format`): purely static, they need **no** running containers, database, or Redis.

```sh
# From the repo root — NOT inside a container
make type-check             # turbo run type-check across all workspaces
make format                 # prettier across the repo
```

## Runtime configuration

Set `PM2_INSTANCES` in the server container environment to choose the production process count. It defaults to `1` per process entry, including the workers entry when enabled.

The production images accept `APP_VERSION` and `GIT_SHA` build arguments for their OCI version and revision labels. The server also exposes these values through its environment, defaulting to `0.0.0` and `unknown`; `GET /ping` returns `{"message":"pong","version":"<string>","commit":"<string>"}`. Web images use the arguments only for labels, without including them in the browser bundle.

`GET /ping` is liveness and checks no dependencies. `GET /ready` is readiness: it returns `200` with `{"status":"ready","checks":{"database":"ok"}}` when the database answers, also checking `redis` when enabled. A failed or timed-out check gives `503`, `status: "unavailable"` and `"failed"` for that check, with details logged only on the server. Checks run in parallel with a two-second timeout each. Both endpoints are unauthenticated; a dependency outage leaves `/ping` healthy.

Use `/ping` for Kubernetes liveness and startup probes, and `/ready` for readiness:

```yaml
livenessProbe:
    httpGet:
        path: /ping
        port: 4000
startupProbe:
    httpGet:
        path: /ping
        port: 4000
    failureThreshold: 30
    periodSeconds: 10
readinessProbe:
    httpGet:
        path: /ready
        port: 4000
    timeoutSeconds: 3
```

Add dependency checks with `registerReadinessCheck(name, asyncCheck)` from `apps/server/src/app/readiness.ts` in a boot hook. A check resolves when ready or throws when unavailable; an empty registry is ready.

When CI and releases are enabled (`ci-github` or `ci-gitlab` in add mode), [RELEASE.md](RELEASE.md) owns the gate, release commands, deployment seam and operator setup. Start there before your first release.

## Getting started on a new project

The template ships ready to run. To turn it into your own product:

- **Set your env.** `make setup` copies `.env.example` to `.env`; fill in `JWT_SECRET` and your database credentials. Firebase and SendGrid are **optional** (leave blank to disable).
- **The name is already wired in.** The generator stamped the app name into everything: the root package, the `@pimasi/lib` workspace scope, and the server / web package names. Nothing needs renaming, and **never rename `@pimasi/utils`**, the external published dependency.
- **Add your first feature.** Start with a schema in `@pimasi/lib`, then a server model, routes + tests, and a web hook + page.
- **Keep the contracts.** Auth (`UserModel`, `UserRoles`, the user JWT) and the session `AsyncLocalStorage` are shared plumbing every feature depends on — extend them, don't fork them.

`WithCredentials` wraps protected pages; pass `onUnauthenticated` to provide login navigation.

## Mobile builds (Cordova)

> This section applies only if you generated the project with **Cordova** enabled (the `apps/web/cordova/` shell is present).

The web app ships to Android/iOS as a [Cordova](https://cordova.apache.org/) hybrid app: the same `apps/web/` SPA is built in cordova mode and packaged by the shell in `apps/web/cordova/`. Cordova mode switches three things in the web build:

- **Relative asset base** so the bundle loads from the WebView's local filesystem, not a web server.
- **Hash-based routing** — `history.pushState` throws on `file://` WebViews, so the app swaps to a hash history.
- **`cordova.js` injection** into `index.html` — the platform supplies the real file at package time; it enables plugins and native lifecycle events (`deviceready`, `pause`, `resume`).

### One-time setup

1. **Install the native toolchain:** JDK 17 + Android Studio (or SDK command-line tools) for Android; Xcode on macOS for iOS.
2. **Create the build config:** `cp apps/web/.env.cordova.example apps/web/.env.cordova` and fill in real values. The API URL must be the deployed API's public URL — a phone cannot reach your Docker localhost.
3. **Install the shell's tooling:** `cd apps/web/cordova && npm install`, then use `npx cordova …` from `apps/web/cordova/` thereafter.

### Build and run

```sh
# 1. From the repo root — build the SPA in cordova mode and copy it into
#    apps/web/cordova/www/. Must run at least once before any cordova CLI command.
npm run cordova:build

# 2. From apps/web/cordova/ — register the platform (first time only)
npx cordova platform add android

# 3. Package / run
npx cordova run android               # debug build on a connected device or emulator
npx cordova build android             # debug .apk, no device needed
npx cordova build android --release   # unsigned release build — sign before shipping
```

Re-run `npm run cordova:build` after every web change — `cordova build` packages whatever currently sits in `apps/web/cordova/www/`.

### Known limitations

- **Google sign-in does not work in the WebView** — Google blocks OAuth from embedded WebViews. Email + password login works; a native sign-in plugin is future work.
- **The app id `com.__APP_SLUG__.app` in `apps/web/cordova/config.xml`** should be agreed before the first store submission; it is immutable once published.
- **Auth tokens live in `localStorage`** inside the WebView (via the web app's `token-storage` module); moving them to a native secure-storage plugin is future work.
