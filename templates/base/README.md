# __APP_SLUG__

A full-stack TypeScript monorepo generated by **create-pimasi-app**. It ships with auth, a database-backed API, and a web app already wired together. Nothing is domain-specific: a single demo `widget` feature shows the end-to-end pattern, and you replace it with your own.

> This README is a guide, not gospel — if in doubt, _always ask your teammates_.

## Architecture

This is a **Turborepo + npm workspaces** monorepo. Three workspaces divide the stack cleanly:

- **Web app** (`apps/web/`) — a browser SPA built with either **TanStack Router + Vite** or **Next.js (App Router)**, depending on how the project was generated. Either way it is a pure client of the Express API, styled with Tailwind 4. UI primitives (`Button`, `Input`, `Spinner`) live in the app's own `components/ui/` (imported as `@/components/ui/*`), themed by the design system chosen at scaffold time — shadcn/ui or bespoke tokens — under the same component API either way. When Cordova is enabled, the same web app packages into Android/iOS via the shell in `apps/web/cordova/`.
- **Server** (`apps/server/`) — Express 5 API on **MongoDB or Postgres**, with **optional Firebase** auth alongside email/password. Three server features are **optional, chosen at scaffold time**, and present only if selected: **background workers** (BullMQ queues + a separate `workers` process), a Redis-backed **`$cache` service**, and Redis-backed **rate limiting** on the auth routes. The database sits behind a repository interface (`apps/server/src/models/*.ts`), so the auth and widget handlers never see the driver.
- **Shared lib** (`apps/shared/lib/`) — `@pimasi/lib`: the runtime **schemas** (request/response shapes) and **values** (enums like `UserRoles`) shared by web and server.

External utilities come from the published **`@pimasi/utils`** package (HTTP client, JSON-schema, logger, typed errors, helpers) — never rename it.

## Dev environment

> Docker & Docker Compose are **required**; Node.js on the host is only for type-checking, formatting, and editor tooling.

The dev environment is **100% dockerised** and must be treated as such: server, web, database, and Redis (when selected) all run in containers. The **only host-side commands** are type-checking and the formatter. `make` targets are the interface; prefer `make` over `npm run`.

```sh
make setup       # copy .env.example to .env if missing + npm install (editor tooling)
make dev         # docker compose up --build --watch (full stack, live reload)
make dev-clean   # reset volumes, then a fresh dev stack
make test        # run every test inside the server container
make type-check  # host-side, static
make format      # host-side, prettier
make update-deps # bump every dependency to latest (npm-check-updates) + install
```

After `make setup`, fill in real `.env` values (ask teammates for secrets). On the Mongo variant, extra `mongo-seed` targets exist for seeding the database.

> The Docker dev stack covers the **browser** app only. Packaging the SPA as an Android/iOS app is a separate, **host-side** flow — see [Mobile builds (Cordova)](#mobile-builds-cordova).

## Build & commands

- The monorepo uses **npm workspaces + Turborepo** for task orchestration; `make` targets wrap the day-to-day commands.
- **Builds and tests run through Docker/make**: `make dev` builds the images, `make test` runs the suite inside the server container.
- The server image transpiles `apps/shared/lib/` and `apps/server/` in one TypeScript project-reference build.
- The **host-side exceptions** are `npm run type-check` (`make type-check`) and prettier (`make format`): purely static, they need **no** running containers, database, or Redis.

```sh
# From the repo root — NOT inside a container
make type-check             # turbo run type-check across all workspaces
make format                 # prettier across the repo
```

## Getting started on a new project

The template ships ready to run. To turn it into your own product:

- **Set your env.** `make setup` copies `.env.example` to `.env`; fill in `JWT_SECRET` and your database credentials. Firebase and SendGrid are **optional** (leave blank to disable).
- **The name is already wired in.** The generator stamped the app name into everything: the root package, the `@pimasi/lib` workspace scope, and the server / web package names. Nothing needs renaming, and **never rename `@pimasi/utils`**, the external published dependency.
- **Replace the demo feature.** Delete the `widget` vertical slice and build your domain the same way — schema in `@pimasi/lib`, model + routes + tests in the server, an API hook + page in the web app. See [Demo feature — widgets](#demo-feature--widgets).
- **Keep the contracts.** Auth (`UserModel`, `UserRoles`, the user JWT) and the session `AsyncLocalStorage` are shared plumbing every feature depends on — extend them, don't fork them.

## Demo feature — widgets

**`widget` is the reference vertical slice** — a minimal CRUD resource scoped per user, wired through every layer so you can copy the shape for real features. It carries no product meaning; delete it once your own domain exists.

The slice touches four layers:

- **Shared schema** — `apps/shared/lib/src/schemas/api/widget.schema.ts`. `WidgetSchema` (the response shape), `CreateWidgetRequestSchema`, `UpdateWidgetRequestSchema`, `WidgetListResponseSchema`, plus `Static` types. Built with `Schema` from `@pimasi/utils/lib/json-schema` — the single source of truth for both runtime validation and TypeScript types.
- **Server model** — `apps/server/src/models/widgets.ts`. One file holds it all: the `WidgetModel` type, the `WidgetsRepo` interface, the `$widgets` implementation for the database this project was generated with, and `toWidgetResponse()` mapping `Date`s to ISO strings. Swapping MongoDB for Postgres swaps only this file.
- **Server routes + tests** — `apps/server/src/handlers/widget/*.route.ts`. `GET`/`POST /widgets` and `GET`/`PATCH`/`DELETE /widgets/:id`, each validating with the shared schema, each scoped to the caller's `user_id`, each shipping a matching `*.test.ts`.
- **Web hook + page** — a data-fetching hook under `apps/web/src/` feeds a `/widgets` page. Mutations revalidate the list after a create or delete.

**Copy this pattern** — schema → model → routes+tests → hook+page — for each real feature you add.

## Mobile builds (Cordova)

> This section applies only if you generated the project with **Cordova** enabled (the `apps/web/cordova/` shell is present).

The web app ships to Android/iOS as a [Cordova](https://cordova.apache.org/) hybrid app: the same `apps/web/` SPA is built in cordova mode and packaged by the shell in `apps/web/cordova/`. Cordova mode switches three things in the web build:

- **Relative asset base** so the bundle loads from the WebView's local filesystem, not a web server.
- **Hash-based routing** — `history.pushState` throws on `file://` WebViews, so the app swaps to a hash history.
- **`cordova.js` injection** into `index.html` — the platform supplies the real file at package time; it enables plugins and native lifecycle events (`deviceready`, `pause`, `resume`).

### One-time setup

1. **Install the native toolchain:** JDK 17 + Android Studio (or SDK command-line tools) for Android; Xcode on macOS for iOS.
2. **Create the build config:** `cp apps/web/.env.cordova.example apps/web/.env.cordova` and fill in real values. The API URL must be the deployed API's public URL — a phone cannot reach your Docker localhost.
3. **Install the shell's tooling:** `cd apps/web/cordova && npm install`, then use `npx cordova …` from `apps/web/cordova/` thereafter.

### Build and run

```sh
# 1. From the repo root — build the SPA in cordova mode and copy it into
#    apps/web/cordova/www/. Must run at least once before any cordova CLI command.
npm run cordova:build

# 2. From apps/web/cordova/ — register the platform (first time only)
npx cordova platform add android

# 3. Package / run
npx cordova run android               # debug build on a connected device or emulator
npx cordova build android             # debug .apk, no device needed
npx cordova build android --release   # unsigned release build — sign before shipping
```

Re-run `npm run cordova:build` after every web change — `cordova build` packages whatever currently sits in `apps/web/cordova/www/`.

### Known limitations

- **Google sign-in does not work in the WebView** — Google blocks OAuth from embedded WebViews. Email + password login works; a native sign-in plugin is future work.
- **The app id `com.__APP_SLUG__.app` in `apps/web/cordova/config.xml`** should be agreed before the first store submission; it is immutable once published.
- **Auth tokens live in `localStorage`** inside the WebView (via the web app's `token-storage` module); moving them to a native secure-storage plugin is future work.

## Project conventions

### Docker

- **Dockerfiles live in the repo root** — named `Dockerfile.<service>` (`Dockerfile.server`, `Dockerfile.web`, and `Dockerfile.mongo` on Mongo). Never place them in subdirectories.
- **The Docker build context is always `.`** (repo root) in `docker-compose.yml`.
- **Every build-time web env var (`VITE_*` for Vite, `NEXT_PUBLIC_*` for Next) in `docker-compose.yml` must also be an `ARG` in `Dockerfile.web`.** The bundler inlines these at build time, so runtime env vars alone are not enough.

### ADR and migration naming — `YYYYMMDDHHMMSS-{kebab-description}`

**Every timestamped generated artefact — ADRs under `docs/adr/`, database migrations, and anything similar — uses the 14-digit filename convention `YYYYMMDDHHMMSS-{kebab-description}`** (e.g. `20260709143000-firebase-uid-trust-on-conflict.md`, `20260709143000-create-initial-indexes.ts`). Run `date +%Y%m%d%H%M%S` when creating one. Never use sequential `0001`, `0002`, … prefixes (they invite gap-counting and cause merge conflicts when authors draft in parallel), and never unix seconds (unreadable at a glance).

Cite ADRs from **code comments and other ADRs by slug**, never by number — `// see ADR firebase-uid-trust-on-conflict`, not `// see ADR-0001`. The slug is stable across filename renames; the prefix is not.

## Code style

| Element                                            | Convention             | Example            |
| -------------------------------------------------- | ---------------------- | ------------------ |
| Internal variables & parameters                    | `camelCase`            | `widgetCount`      |
| External contract fields (API, DB, queue messages) | `snake_case`           | `created_at`       |
| Functions                                          | `camelCase`            | `createWidget()`   |
| Types / Classes                                    | `PascalCase`           | `WidgetModel`      |
| Top / module-level constants                       | `UPPER_SNAKE_CASE`     | `MAX_RETRIES`      |
| File names                                         | `lowercase-kebab-case` | `create-widget.ts` |

- All variables inside a function that are **not** module-level must use `let`, not `const`.
- All module-level declarations must use `const`.

### Tooling — TypeScript + Prettier, never ESLint

**All source is TypeScript** — no `.js`/`.jsx` app code. The correctness gate is the compiler (`make type-check`); the style gate is Prettier (`make format`, enforced by the pre-commit hook). **Never add ESLint** — no configs, no plugins, no `eslint-*` dependencies, in any workspace. If a rule feels missing, it belongs in the type system or in this README, not in a linter.

### Language — British English

**British English is the default for all prose AND for new code identifiers: docs, comments, commit messages, UI copy, error messages, function names, variable names, types, API field names.** Use `organise`, `colour`, `behaviour`, `centre`, `licence` (noun) / `license` (verb), `realise`, `analyse`, `defence`, `normalise`, `-isation` endings, etc. Do **not** "normalize" British spellings to American because a spellchecker flags them — the spelling is intentional.

When **inventing** a new identifier, prefer the British form (`normaliseEmail`, not `normalizeEmail`; `colourPalette`, not `colorPalette`). The narrow exception is **renaming** an existing identifier that's already US-spelled and has many callers — leave it if the rename would just be churn; otherwise rename it. Vendor APIs we call (Firebase's `authorizedDomains`, the HTTP `Authorization` header, Tailwind's `text-color-*`) keep their wire-format casing because they're not ours to change.

### Naming — case by boundary

**`snake_case` marks an external contract; everything internal is `camelCase`.** The boundary is serialisation: a field that crosses the wire or hits a datastore keeps its `snake_case` wire shape, and a name that only ever lives inside the process uses normal TypeScript casing.

- **`snake_case` (external contracts):** API request/response fields, DB columns/document fields, queue/message payloads, JWT claims. These are the shapes in `@pimasi/lib` schemas and `apps/server/src/models/` (`created_at`, `password_hash`, `user_id`, `email_verified`).
- **`camelCase` (internal code):** local variables, function parameters, internal option/config objects, React state setters (`const [name, setName] = useState()`).

```ts
// GOOD — internal options object, never serialised: camelCase keys
interface RateLimitOptions {
    bucket: string;
    windowSeconds: number;
    maxRetries: number;
}

// GOOD — API schema, a wire contract: snake_case fields
export const WidgetSchema = Schema.Object({
    id: Schema.String(),
    user_id: Schema.String(),
    created_at: Schema.String(),
});

// BAD — casing leaking across the boundary
interface RateLimitOptions {
    window_seconds: number; // ❌ internal, so camelCase
}
export const WidgetSchema = Schema.Object({
    createdAt: Schema.String(), // ❌ wire field, so snake_case
});
```

The payoff: a `snake_case` key signals "this exact name appears on the wire or in the database", so a grep for `created_at` finds every use of the contract field and nothing else. Vendor APIs are external contracts too (Firebase Admin's `errorInfo`, the HTTP `Authorization` header): match their casing at the boundary, `camelCase` internally either way.

### Implicit / braceless bodies — only when they fit on one line

**Do not use implicit-body syntax (arrow function implicit return, braceless `if` / `else` / `else if`) when the body wraps to a new line or doesn't fit on a single line under 80 characters.** When it doesn't fit, use an explicit block body — `async`/`await` with `{ … }` for arrow functions, `{ … }` for `if`/`else`.

```ts
// BAD — braceless if with body on a new line
if (body.starts_at !== undefined) updates.starts_at = new Date(body.starts_at);

// GOOD — body wraps to a new line, so use braces
if (body.starts_at !== undefined) {
    updates.starts_at = new Date(body.starts_at);
}

// GOOD — fits on one line, braceless is fine
if (foo) return;
```

## Backend conventions

### IDs — ULID string ids everywhere

**Every row/document has its own `id: string` field generated by `ulid()` from the `ulid` npm package.** Use `id` in all queries, references, foreign keys, and API responses. (On MongoDB the driver still creates an `_id` under the hood — ignore it; never use `_id` or `ObjectId`.)

- Schema field: `id: string` (typed in the model, populated at insert time).
- Generation: `import { ulid } from "ulid"; let id = ulid();` — inline at the call site, not via a wrapper.
- Foreign keys follow the same convention: `user_id: string`, `widget_id: string`, etc., all storing ULIDs.
- Test seeders and route handlers all use `ulid()` directly — match that pattern when adding a new collection/table.

Why: ULIDs are sortable by creation time, URL-safe, and human-readable, which makes them better for logs, debugging, and API surfaces. Consistency across the schema matters more than any one ID's properties — do not introduce a different ID scheme for a "special" table.

### Database — one repository interface, two implementations

**The server never talks to the database driver directly.** Each file in `apps/server/src/models/` is self-contained: it defines the domain type, the `*Repo` interface, and the concrete implementation for this project's database (MongoDB or Postgres/Kysely) in one place. Handlers depend only on the exported `$users` / `$widgets` objects. To add a new persisted resource, create one `models/<resource>.ts` with its type, its `*Repo` interface, and the implementation together — do not reach for the raw client inside a handler.

### Schemas — `@pimasi/utils`, never Zod or ajv

**All runtime schemas use `Schema` from `@pimasi/utils/lib/json-schema`.** Do not introduce Zod, ajv, or any other validation library — schemas, request/response validation, and type inference all go through `@pimasi/utils`. This applies everywhere: `apps/shared/lib/src/schemas/api/*`, request-body validation in routes (`Schema.validate(req.body, RequestSchema)`), and any new value-object schema you might be tempted to type with another library.

```ts
// GOOD — @pimasi/utils Schema
import { Schema, Static } from "@pimasi/utils/lib/json-schema";

export const FooRequestSchema = Schema.Object({
    foo_id: Schema.String(),
    quantity: Schema.Optional(Schema.Number()),
});
export type FooRequest = Static<typeof FooRequestSchema>;

// BAD — never import zod or ajv
import { z } from "zod"; // ❌
import Ajv from "ajv"; // ❌
```

Discriminated unions use `Schema.AnyOf([...])` with `Schema.Const("...")` discriminators. `Static<typeof X>` infers the TypeScript type from the schema. Match what existing schemas in `apps/shared/lib/src/schemas/api/*` already do — that is the canonical pattern.

## Frontend conventions

### Tailwind CSS — colour usage

**Never use bespoke/hardcoded Tailwind colour classes** (e.g. `bg-purple-600`, `text-blue-500`). All colours must reference the semantic design tokens defined in the web app's theme stylesheet (`src/styles.css` on TanStack, `app/globals.css` on Next.js). Both design systems (shadcn/ui and bespoke) define the **same shadcn-standard token vocabulary**, so pages never fork per design:

| Token pair                           | Use for                                          |
| ------------------------------------ | ------------------------------------------------ |
| `background` / `foreground`          | page background and default text                 |
| `card` / `card-foreground`           | elevated surfaces (cards, panels) and their text |
| `popover` / `popover-foreground`     | floating surfaces (menus, dropdowns, tooltips)   |
| `primary` / `primary-foreground`     | primary actions and the text on them             |
| `secondary` / `secondary-foreground` | secondary actions and the text on them           |
| `muted` / `muted-foreground`         | subdued surfaces and secondary text              |
| `accent` / `accent-foreground`       | hover/highlight surfaces and their text          |
| `destructive`                        | errors and destructive actions                   |
| `border` / `input` / `ring`          | borders, form-control borders, focus rings       |
| `success` / `success-foreground`     | positive status (the one PIMASI extension token) |

`--radius` drives border radii. The usual patterns:

- **Page layout:** `bg-background text-foreground` on the root/body
- **Cards/panels:** `bg-card text-card-foreground border border-border rounded-lg`
- **Primary buttons:** `bg-primary text-primary-foreground hover:bg-primary/90` — hover states always use opacity modifiers (`/90`, `/80`), never `-hover` token variants (they don't exist)
- **Links:** `text-primary hover:underline`
- **Status indicators:** `text-success` for positive, `text-destructive` for errors

```tsx
// BAD — hardcoded / arbitrary colours
<button className="bg-cyan-500 text-white hover:bg-cyan-600">
<div className="bg-[#030B0E] text-[#f2f2f2]">

// GOOD — semantic tokens
<button className="bg-primary text-primary-foreground hover:bg-primary/90">
<div className="bg-background text-foreground">
```

### HTTP requests — `@pimasi/utils/lib/http` only

**Never use raw `fetch()` or `axios`, anywhere in the repo, including tests.** `@pimasi/utils/lib/http` (an axios-compatible HTTP client over native fetch) is the only HTTP client. In the web app that means the `$server` client built on it: its base URL comes from the web app's public API env var (`VITE_API_URL` on the Vite/TanStack app, `NEXT_PUBLIC_API_URL` on the Next.js app), and it auto-attaches the JWT auth token via a request interceptor — no manual `Authorization` header needed. Server tests make their HTTP calls through the `$test` helpers, which sit on the same client.

```tsx
import { $server } from "@/services/server"; // path may vary per frontend

// GET
let res = await $server<Widget[]>({ method: "GET", url: "/widgets" });
let widgets = res.data;

// POST
let res = await $server<{ token: string }>({
    method: "POST",
    url: "/auth/login-with-password",
    data: { email, password },
});
let token = res.data.token;
```

```tsx
// BAD — raw fetch with manual headers
let res = await fetch(`${API_BASE}/widgets`, {
    headers: { Authorization: `Bearer ${token}` },
});

// GOOD — $server(config) handles base URL and auth
let res = await $server<Widget[]>({ method: "GET", url: "/widgets" });
```

The bearer token `$server` attaches comes from the web app's `token-storage` module — **never read or write `localStorage` directly for auth tokens**; the module is the single place to swap the backing store later.

## Testing

### Tests — all of them, always inside Docker

**Every test in this repo MUST run inside its Docker container — never on the host.** PIMASI apps are Docker-first; this is a hard rule, not a preference. The suite is an integration suite: it talks to the live database (and Redis, when selected) from the compose stack, uses the same env vars as the running server, and assumes the same Node version, native modules, and filesystem layout. Running on the host gives misleading results. This applies to **every current and future test target** in the repo, not just the server.

```sh
# GOOD — run the full suite (wraps docker exec into the server container)
make test

# GOOD — scope to a single file or pattern
make test ARGS="src/handlers/widget/list-widgets.test.ts"
make test ARGS="-t 'creates a widget'"

# BAD — running on the host
cd apps/server && npx vitest          # ❌ wrong DB/Redis, wrong env, will mislead you
```

If `make test` fails because the stack isn't running, bring it up first (`make dev`, or `docker compose up -d` for a detached stack) — do not fall back to the host. If you add a new test target, wire it into `make test` (or a sibling make target that also execs into a container) — never introduce a host-only test path.

### Server endpoint testing

**Every server endpoint MUST ship with a test.** Creating a new `*.route.ts` without a matching `*.test.ts` is not allowed — the two files land in the same commit. Tests assume a running server and verify behaviour via HTTP calls + database assertions.

- Use the `$test` helper from `apps/server/src/test/helpers.ts` for seeding, HTTP calls, DB access, and cleanup.
- Test both success and error cases (auth, validation, DB side effects).
- Use `$test.seed()` / `$test.teardownSeed()` for the test-data lifecycle.
- Verify side effects by querying `$test.db.*` directly.
- See existing tests under `apps/server/src/handlers/` for patterns.

## AI agent rules

This section is for rules that apply **specifically to AI agents** (Claude, Codex, GitHub Copilot, etc.) — how to behave when given a task. Everything above (code style, backend/frontend conventions, testing) applies to all contributors regardless of tooling; only put a rule here if it would not make sense as advice to a human teammate.

The agent-specific entry points ([CLAUDE.md](CLAUDE.md), [.codex](.codex), [.github/copilot-instructions.md](.github/copilot-instructions.md)) all redirect here so the rules stay centralised across tools. **When asked to add, update, or remove a rule, edit this README** — never add rules to the agent-specific files. Coding/design rules go in the matching section above; behavioural rules go in this section.

### Clarify before deciding — ask, don't guess

**This is the single most important rule in this section.** A one-line question costs nothing; a wrong assumption costs a re-do. When a task has an ambiguous choice, a tradeoff worth flagging, an invented name/threshold/default, or ripple effects beyond its immediate scope, **stop and ask the user** before proceeding.

Moments that warrant a question, not a guess:

- Two reasonable implementations exist (collapse two endpoints vs. keep both; add a new route vs. modify an existing one).
- A change has ripple effects outside the immediate scope (deleting a public API, renaming a field on the wire, schema changes).
- The user's phrasing could reasonably mean more than one thing.
- You'd need to invent a name, threshold, default, or UX affordance that isn't obvious from context.
- You notice something odd or incorrect adjacent to the task (pre-existing bug, redundant field, dead code) — surface it and ask whether it's in scope, don't silently "fix" it.

Prefer: "I'm about to do X — or did you mean Y?" over guessing and explaining afterwards.

### No AI-authored comments in code — ever

**Agents never write comments, full stop. Comments are a human-only channel: they carry intent, a deliberate warning, or hard-won context that a person chose to leave for other people. Only users write them; if a comment is in the code, a human put it there on purpose.** Make the code self-explanatory through names and structure instead; when something genuinely needs explaining, put it in the commit/PR description or ask whether it warrants a (human) comment.

- Never narrate what the code does (`// loop over items`, `// increment the counter`), restate the next line, or sprinkle `// TODO` / `// NOTE` markers.
- Do not add or re-expand JSDoc / docblocks on code you touch unless the user explicitly asks for it.
- Do not delete or reword a human's existing comment as an incidental side effect of an unrelated edit — that context is theirs, not yours to tidy.
- **Functional / directive comments are exempt** — they are machine instructions, not prose: `// @ts-expect-error`, `// @ts-ignore`, `// eslint-disable*`, `// prettier-ignore`, `#!` shebangs, and similar pragmas stay, and you still add them when they are functionally required.

### No plan mode — plans live in `.scratch/`

**Do not use your tool's plan mode.** When a task needs a plan, write it as a markdown file under the gitignored `.scratch/` folder at the repo root, then validate it with the user before implementing. A plan file can be read, edited, and re-reviewed by anyone at any point; plan mode traps the same content inside one tool's session.

### Generated content follows the timestamp convention

**Anything you generate that is timestamped by name (migrations, ADRs, similar artefacts) is named `YYYYMMDDHHMMSS-{kebab-description}`**: run `date +%Y%m%d%H%M%S` for the prefix. ### Keep this README in sync

**This README is the canonical source of truth for project rules — keep it up to date in the same commit as the change that makes a section stale, never as a follow-up.** Humans usually notice when a doc drifts from reality; agents won't, so this rule exists to force the update.

Trigger an update when you:

- Add, rename, or remove an app or shared package under `apps/` (update both the **Architecture** bullets and the **Project structure** tree).
- Add a new top-level directory or root-level config file a new contributor would need to know about.
- Change how the dev environment runs: new `make` targets or top-level `npm run` scripts, new required env vars in `.env.example`, new docker-compose services exposed on the host.
- Change build/release flows (Cordova mode flags, new build outputs, new Dockerfile targets at the repo root).
- Add, change, or remove a coding/design convention, testing rule, or documentation workflow — edit the matching section above; for a behavioural agent rule, edit this section.

You do **not** need to touch this README for route additions, schema tweaks, internal refactors, or bug fixes that live entirely inside one app and don't change its public surface. When in doubt, ask: "would a teammate cloning the repo today be misled by what the README says?" If yes, update it.
