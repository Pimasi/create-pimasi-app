# create-pimasi-app — DESIGN / CONTRACT

`create-pimasi-app` is a `create-next-app`-style scaffolder. It prompts the user, then composes a full-stack TypeScript monorepo from **template fragments** under `templates/`.

The fragments themselves are the source of truth for code; this document is the contract they must honour — the prompt matrix, the composition rules, the locked cross-fragment interfaces, and the conventions. When a fragment and this document disagree, fix one of them in the same change.

## The prompts

1. **Frontend** — `tanstack` (React 19 + Vite + TanStack Router SPA) or `nextjs` (Next.js App Router, **frontend only** — it is a client of the Express API, NOT full-stack Next).
2. **Cordova** — yes/no (mobile packaging of the web app).
3. **Database** — `mongo` (MongoDB driver) or `postgres` (**Kysely** query builder over `pg`).
4. **Workers** — yes/no, `--yes` default **no**: BullMQ queues + a separate workers process; email dispatch enqueues instead of sending inline.
5. **Cache** — yes/no, `--yes` default **yes**: a `$cache` service (`get`/`set`/`del`/`getOrSet`) on Redis.
6. **Rate limiting** — yes/no, `--yes` default **yes**: the Redis-backed `RATE_LIMIT` middleware replaces base's no-op.
7. **WebSockets** — yes/no, `--yes` default **no**: a JWT-authenticated `/ws` endpoint with a per-user socket registry and cross-instance fan-out over the `$bus` messaging seam (Redis-backed today), plus web client hooks for the chosen frontend (shipped, NOT auto-mounted). See "LOCKED websocket contracts" below.
8. **Design system** — `shadcn` (shadcn/ui conventions: stock zinc light+dark theme, cva/clsx/tailwind-merge, `components.json`) or `bespoke` (an in-house dark palette, zero extra deps). See "LOCKED design-system contract" below.
9. **CI and releases**: `github`, `gitlab`, or `none`, shown after design; `--yes` default **none**. A host adds the request gate, manual promotion and release notes; see "LOCKED release contract" below. With a host, **Only Maintainers can release?** follows, `--yes` default **yes**, and its answer is written to `scripts/release/config.sh` as `RELEASE_MAINTAINERS_ONLY`.

Redis is not a prompt; it ships exactly when something needs it. The `server/redis` fragment (the node-redis `$redis` client and `redis` dependency) composes when workers OR cache OR rate limiting OR websockets is on; workers uses dedicated node-redis connections through BullMQ. `REDIS_URL` is required at runtime when ANY of the four server axes (workers/cache/rate limiting/websockets) is on; with all four off the project has no Redis at all.

The Express **server is shared** across both frontends. The database choice swaps only the server's data-access layer, behind a repository interface — the auth handlers never see the driver. The design choice swaps only `apps/web`'s theme CSS + `components/ui/*` implementations, behind a shared component API and token vocabulary — pages are written once. The server axes compose through two extension seams: **seam files** (base ships a working redis-free implementation of a single file behind a stable exported API, and the fragment overwrites just that file — no-op → Redis `RATE_LIMIT`; direct-send → enqueueing `handlers/email/dispatch.ts`) and **autoloaded boot hooks** (`*.boot.ts` files that `backend.ts` discovers and runs before listen — how workers mounts bull-board and websockets attaches the `/ws` upgrade handler, without either fragment overwriting `backend.ts`).

## Composition model

```
templates/
  base/                     # copied ALWAYS (root tooling, shared/lib, server FRAMEWORK)
  frontend/tanstack/        # -> apps/web (+ Dockerfile.web)   [React/Vite SPA]
  frontend/nextjs/          # -> apps/web (+ Dockerfile.web)   [Next.js app]
  db/mongo/                 # server DB overlay + mongo/ + Dockerfile.mongo
  db/postgres/              # server DB overlay (Kysely)
  server/redis/             # $redis node-redis client         [copied when workers OR cache OR rate limiting OR websockets]
  server/workers/           # BullMQ queues + workers process  [copied when workers]
  server/cache/             # $cache service over $redis       [copied when cache]
  server/rate-limit/        # Redis-backed RATE_LIMIT seam     [copied when rate limiting]
  websockets/server/        # /ws endpoint + registry + $bus + lib event schema [copied when websockets]
  websockets/tanstack/      # web WS client + provider + hooks (NOT auto-mounted)
  websockets/nextjs/        #   (same, Next file layout)
  design/shadcn/tanstack/   # theme CSS + components/ui + cn + components.json + pkg partial
  design/shadcn/nextjs/     #   (same, Next file layout)
  design/bespoke/tanstack/  # in-house palette under the SAME token names + simple components
  design/bespoke/nextjs/    #   (same, Next file layout)
  cordova/tanstack/         # cordova shell + web package.json partial (build:cordova)
  cordova/nextjs/           # cordova shell + next static-export config
  ci/common/               # release scripts, tests, compose overrides and RELEASE.md
  ci/github/               # GitHub workflows and host adapter [copied when ci=github]
  ci/gitlab/               # GitLab pipeline and host adapter [copied when ci=gitlab]
  legacy/0.2.0/            # published pristine snapshots; never copied into apps
```

UI primitives live inside `apps/web` (supplied by the design overlay) — there is deliberately no shared UI package.

CLI compose order (later copies overlay earlier; paths are disjoint — no clobber — except package.json, which is MERGED, and the seam files the server fragments deliberately overwrite):

1. copy `base/` → target
2. copy `db/<db>/` → target
3. server fragments, each conditional: `server/redis/` if workers OR cache OR rate limiting OR websockets; `server/workers/` if workers; `server/cache/` if cache; `server/rate-limit/` if rate limiting; `websockets/server/` if websockets
4. copy `frontend/<frontend>/` → target; if websockets: copy `websockets/<frontend>/` → target (adds the WS client + hooks into `apps/web`)
5. copy `design/<design>/<frontend>/` → target
6. if cordova: copy `cordova/<frontend>/` → target
7. if ci is not `none`: copy `ci/common/`, then `ci/<ci>/` → target; their paths are disjoint and neither has a package.json partial
8. **merge** `apps/server/package.json` = deepMerge(base, db partial, selected server-fragment partials — including websockets/server's); **merge** `apps/web/package.json` = deepMerge(frontend, design partial, cordova partial if selected)
9. **generate** `docker-compose.yml`, `.env.example`, and a "## Stack" block in `README.md` from the selections (CLI code, not template files)
10. **placeholder replace + workspace rename** across all text files
11. `git init -b main`, falling back to `git init` and `git symbolic-ref HEAD refs/heads/main` on older Git (+ optional `npm install`)

### Placeholders and the per-project workspace rename

- `__APP_SLUG__` — kebab app name. Appears in: root `package.json` "name", `apps/web/cordova/config.xml` (id `com.__APP_SLUG__.app` + name), README H1, the cordova shell package name, and release tooling. The replacement pass includes shell, YAML and Markdown files.
- **Templates keep literal workspace and container names** so the template sources stay valid, greppable code. At generate time the CLI renames them by exact-token replacement using the app name:
  - `@pimasi/lib` → `@<slug>/lib` (package name, every import, tsconfig paths, transpilePackages)
  - `pimasi-server` → `<slug>-server`, `pimasi-web` → `<slug>-web` (package names, turbo filters, Dockerfile workspace flags, Makefile)
  - `pimasi-mongo` → `<slug>-mongo`, `pimasi-redis` → `<slug>-redis`, `pimasi-postgres` → `<slug>-postgres` (container names in Makefile/seeds.mk; the compose generator emits the renamed names directly)
  - `pimasi_auth_token` → `<slug_with_underscores>_auth_token` (web localStorage key)

  So an app named `acme` imports `@acme/lib/schemas/...`.

- **Never rename `@pimasi/utils`** (external published dep). The exact-token needles above cannot match it — never add a bare `pimasi` or `@pimasi/` needle.
- **`templates/` is prettier-ignored in this repo** (`.prettierignore`): markdown formatting mangles `__APP_SLUG__` in headings into `**APP_SLUG**`, which silently breaks the rename.
- **`.gitignore` ships as `_gitignore`.** npm strips every `.gitignore` at any depth from a published tarball, whatever `files` or the root `.npmignore` say (`npm-packlist`'s built-in rules). A literal `.gitignore` inside a fragment therefore never reaches users. Fragments store it as `_gitignore`; `copyDir` and add mode write it as `.gitignore` (`RENAME_ON_COPY` in `compose.ts`, the only file-name rename the CLI performs). Never add a literal `.gitignore` inside a fragment directory.
- **`templates/.gitignore` is repo hygiene, not template content.** It keeps strays (`.env`, `*.pem`, `.scratch/`, build output) out of git and out of the tarball for the whole template tree: a nested ignore file still filters `npm pack` even though `files` makes the root ones inert. Composition starts inside fragment directories, so the CLI never copies it, and npm strips it from the tarball. Keep its patterns clear of anything a fragment tracks (`next-env.d.ts`, `.env.cordova.example`).

## LOCKED design-system contract

Both design overlays implement the SAME component API and the SAME token vocabulary (shadcn/ui's), so frontend pages are written once and never fork per design.

### Component API (identical import paths + props in both designs, both frontends)

- `@/components/ui/button` → `export function Button(props)` — extends `React.ButtonHTMLAttributes<HTMLButtonElement>` with `variant?: "default" | "secondary" | "outline" | "ghost" | "destructive" | "link"` and `size?: "default" | "sm" | "lg" | "icon"`. (shadcn overlay: the stock cva-based button, also exports `buttonVariants`.)
- `@/components/ui/input` → `export function Input(props)` — extends input attrs. MUST hide native number spinners (`[appearance:textfield] [&::-webkit-outer-spin-button]:appearance-none [&::-webkit-inner-spin-button]:appearance-none`).
- `@/components/ui/spinner` → `export function Spinner({ className? })` — a small animated loading indicator.
- `@/lib/utils` → `export function cn(...inputs)` — shadcn overlay: `clsx` + `tailwind-merge`; bespoke overlay: `inputs.filter(Boolean).join(" ")` with no deps.
- The FRONTEND template (not the design overlay) owns `@/components/loading-page` — a full-page centred loader built on `Spinner` — because it is identical across designs.

For tanstack, `@/` maps to `./src/`; the design overlay ships `src/components/ui/*`, `src/lib/utils.ts`, and `src/styles.css` (the Tailwind entry: `@import "tailwindcss"`, theme tokens, `@source`). For nextjs, `@/` maps to the app root; the overlay ships `components/ui/*`, `lib/utils.ts`, and `app/globals.css`. The frontend template does NOT ship these files — the overlay always provides them.

## LOCKED repository interface (the DB abstraction)

The base server code depends ONLY on the surface below. **Base ships NO `models/` directory** — the DB overlay owns `apps/server/src/models/users.ts` outright, and the file is self-contained: domain type + `*Repo` interface + the concrete `$users` implementation for that database, together in one file. Both overlays must export the identical surface so base handlers compile against either.

```ts
// @pimasi/lib/values/auth  -> enum UserRoles { ADMIN="admin", USER="user" }

export interface UserModel {
  id: string;
  created_at: Date;
  name: string;
  email: string; // normalised lowercase
  email_verified: boolean;
  password_hash?: string; // undefined when unset
  firebase_id?: string; // undefined when unset
  disabled_at?: Date | null;
  roles: UserRoles[];
}

export interface UsersRepo {
  findById(id: string): Promise<UserModel | null>;
  findByEmail(email: string): Promise<UserModel | null>; // email pre-normalised by caller
  findByFirebaseOrEmail(
    firebaseId: string,
    email: string,
  ): Promise<UserModel | null>;
  insert(user: UserModel): Promise<void>;
  update(id: string, changes: Partial<UserModel>): Promise<void>; // $set semantics; only provided keys change
}
```

### Overlay model-file shape (single file: type + interface + implementation)

```ts
import { UserRoles } from "@pimasi/lib/values/auth";
import { $mongo } from "../services/db";   // or { $db, Database } in the Kysely overlay
export interface UserModel { ... }          // as above
export interface UsersRepo { ... }          // as above
export const $users: UsersRepo = { ...concrete driver implementation... };
export function normaliseEmail(email: string): string { return email.trim().toLowerCase(); }
```

The interface blocks are duplicated verbatim between the two DB overlays — keep them in sync with the contract above; only one overlay ships per generated project.

### Behavioural contracts the handlers rely on

- `parse-session` loads the user via `findById` and deletes `password_hash` from the object before storing it in the ALS session — the hash never sits in request context.
- `get-session-user` re-fetches via `findById` to surface `password_hash ?? ""` (the web app branches set-password vs change-password on it).
- `backend.ts` imports `{ runMigrations } from "./migrations"` — the DB overlay owns that module.
- Password-reset tokens are **stateless** — no server-side token store. `handlers/auth/password-reset-token.ts` signs a JWT with `$env.JWT_SECRET` (~1 h expiry, via `jsonwebtoken`) carrying `{ type: "password_reset", user_id, pwd }`, where `pwd` is the first 16 hex chars of `sha256(password_hash ?? "")`. Verification checks the type, the expiry, and that `pwd` still matches the user's current `password_hash` — completing a reset changes the hash, so the token cannot be replayed (single-use without state). This implementation ships always; no fragment overwrites it.
- `$jwt.verify` (`utils/jwt.ts`) **throws unless the decoded payload has `type === "user"` and a string `user_id`** — it never coerces. Reset tokens share `JWT_SECRET`, so without this check a 1-hour reset token would authenticate as a full session on HTTP (`parse-session`) and on the `/ws` upgrade. All three call sites (parse-session, rate-limit keying, ws-server) treat a throw as "no user".

## LOCKED boot-hook contract (base extension seam)

Base ships an autoloaded boot-hook pattern mirroring the `*.route.ts` / `*.queue.ts` / `*.cli.ts` idiom, so fragments extend server startup without overwriting `backend.ts`:

- `apps/server/src/app/boot.ts` — `interface BootContext { app: Express; httpServer: Server; isProduction: boolean }`, `interface Boot { name: string; handler: (ctx: BootContext) => Promise<void> | void }`, and a `Boot(boot)` factory using the prototype-marker pattern (`_proto` + `Object.setPrototypeOf` + `Boot.isBoot`, same shape as `app/cli-command.ts`).
- `backend.ts` — after `createServer(app)` and BEFORE listen: glob `./**/*.boot.{ts,js}` under `src/`, require each file (warn-and-skip on load error, like `autoLoadRoutes`), collect exports where `Boot.isBoot`, and for each: `await handler({ app, httpServer: server, isProduction })` then a `$logger.debug("boot hook ran: <name>")`.
- Base ships ZERO `*.boot.ts` files — the loop is a no-op until a fragment adds one (workers: `bull-board.boot.ts`; websockets: the `/ws` upgrade handler).

## LOCKED readiness contract (base extension seam)

`GET /ping` remains an unauthenticated liveness probe with version and commit, and never checks dependencies. `GET /ready` is an unauthenticated readiness probe: HTTP 200 with `{ "status": "ready", "checks": { "database": "ok" } }` when every registered check passes, or HTTP 503 with `status: "unavailable"` and each check marked `"ok"` or `"failed"`. An empty registry is ready. Errors are logged on the server and never returned in the response.

`apps/server/src/app/readiness.ts` exports `registerReadinessCheck(name, check)` and `runReadinessChecks()`. Registration accepts a named async check and returns a function that restores the previous registration, allowing isolated test overrides. Checks run in parallel with a two-second timeout per check. Fragments add boot hooks through the existing boot seam: Mongo registers `database` using a ping command, PostgreSQL registers `database` using `select 1`, and `server/redis` registers `redis` using PING. Fragments do not overwrite the registry or route. The shared response schema lives beside the ping schema, and route tests prove dependency failure returns 503 while `/ping` stays 200.

## LOCKED websocket contracts

### Server

- **Endpoint**: `ws://host/ws?token=<user JWT>`. A `*.boot.ts` hook (via the boot-hook seam) attaches a `ws`-package `WebSocketServer` to the HTTP server's upgrade path. The upgrade optionally checks `Origin` against `WS_ALLOWED_ORIGINS` (comma-separated; empty = any, rejects 403 otherwise), verifies the token with `$jwt.verify`, requires `parsed.type === "user"`, rejects 401 otherwise. The authenticated identity is passed from `verifyClient` to the connection handler via a `WeakMap` keyed by the request (no `req` mutation). `maxPayload` is capped at 10 MiB (the endpoint is push-only; unexpected inbound frames terminate the socket). Sockets are registered per `user_id` with heartbeat (server ping every 60 s, watchdog terminates after 90 s without pong) and are closed with code 4001 when the token's `exp` passes, so a live connection cannot outlive its credential. The boot hook drains sockets on `SIGTERM`/`SIGINT` (each client closed 1001, then `wss.close()`).
- **`services/websocket.ts`** — the app-facing `$websocket` service, owning the local `Map<string, Set<WebSocket>>` registry + `$bus` fan-out. It declares and EXPORTS the module-level channel `wsDispatch = $bus.channel<{ user_id, event }>("ws.dispatch")` — EPHEMERAL by design (see the bus contract below); tests import `wsDispatch` rather than re-declaring the channel. API: `send(userId, event: WSEvent)` / `sendToMany(userIds, event)` publish `{ user_id, event }` (snake_case — a bus message is an external contract) on `ws.dispatch`; `isUserOnline(userId)` (LOCAL knowledge only — it cannot see sockets on other instances); `register(userId, ws)` returning the socket's idempotent `release()` callback (called only by `ws-server`: register on connect, release on close). `register` caps concurrent sockets per user at 20, evicting the oldest. A module-level subscription on `ws.dispatch` (retried with backoff on failure so a transient boot-time outage self-heals) validates each event against `WSEventSchema` and delivers to local sockets through a guarded `sendIfOpen` (readyState check, terminates a consumer whose buffer exceeds 1 MiB, send errors caught and warn-logged). Because `send` publishes rather than writing to sockets, ANY process (backend instance, worker) can push to a user whose socket lives on another instance.
- **`services/bus.ts` + `services/bus-driver.ts`** — the messaging **transport seam**, split so a future backend swaps ONLY the driver file. `bus.ts` owns the app-facing API and every semantic rule: `$bus.channel<T>(name, { durable?, maxLen? })` declares a channel ONCE (a registry returns the same instance on an identical redeclaration and throws on a conflicting one; names must match `[A-Za-z0-9][A-Za-z0-9._-]*` — dot-separated words, legal as a Kafka topic, free of NATS wildcards). A channel exposes `publish(payload)` (fire-and-forget; the call is identical whatever the delivery mode) and `subscribe(handler, { group? })` returning an async unsubscribe. Payloads are serialised with `jsonStringify`/`jsonParse` from `@pimasi/utils/lib/helpers` (invalid JSON is warn-and-dropped), and a throwing handler is caught and error-logged — a handler failure never crashes the process and is never retried by the bus (retries, backoff and inspection are `$bull`'s job: **jobs go to `$bull`, events go to `$bus`**). Semantics: an EPHEMERAL channel (the default) is live broadcast — every subscriber on every instance sees every message, nothing is stored. A DURABLE channel is a retained log (`maxLen` entries, default 10 000, trimmed approximately): a bare `subscribe` tails new messages from subscribe time; `subscribe` with `group` makes competing consumers — each message reaches ONE member of the group, progress survives restarts, delivery is at-least-once (acked after the handler; deliveries abandoned by a dead consumer are reclaimed after 60 s), and a NEW group starts from the beginning of the retained log, so independent groups each receive their own full copy. `group` on an ephemeral channel throws — Redis has no ephemeral group primitive, and the restriction keeps every combination portable. `bus-driver.ts` is the Redis implementation behind the `BusDriver` interface exported by `bus.ts`: ephemeral = Redis pub/sub on a lazily-created duplicated subscriber connection (`$redis.duplicate()` + connect — node-redis subscriber connections cannot run normal commands; a failed connect is not cached, so callers can retry); durable = one Redis Stream per channel (`XADD` with `MAXLEN ~`; groups via idempotent `XGROUP CREATE … 0 MKSTREAM` + blocking `XREADGROUP`/`XACK` with an `XAUTOCLAIM` sweep; tail via blocking `XREAD` from the stream's last-generated id; one duplicated connection per stream subscription, destroyed on unsubscribe and `$bus.close()`). NATS (core/JetStream) and Kafka are anticipated future drivers, added by overwriting `bus-driver.ts` alone. App code — `$websocket` included — talks to channels, never to `$redis`, for messaging. `ws.dispatch` stays EPHEMERAL by design: dispatch relies on BROADCAST delivery (every server instance must receive every message to check its local registry), and durability would replay events at sockets that died with their instance.

### Shared schema (`@pimasi/lib`)

`apps/shared/lib/src/schemas/api/ws-events.schema.ts`, built with `Schema`/`Static` from `@pimasi/utils/lib/json-schema`: `WSResourceChangedEventSchema` `{ type: Schema.Const("resource_changed"), resource: Schema.String(), id: Schema.Optional(Schema.String()) }`, `WSNotificationEventSchema` `{ type: Schema.Const("notification"), title: Schema.String(), body: Schema.Optional(Schema.String()) }`, `WSEventSchema = Schema.AnyOf([...])`, plus the `Static` type `WSEvent` and helpers `WSEventType = WSEvent["type"]` and `WSEventByType<T> = Extract<WSEvent, { type: T }>`.

### Web client (both frontends, layout-adjusted; native browser `WebSocket`, no new deps)

- A ws service: `connectWebSocket(token)`, `disconnectWebSocket()`, `addMessageHandler`/`removeMessageHandler`; exponential reconnect with jitter capped at 30 s; url = the API base with http→ws + `/ws?token=...`.
- A `WebSocketProvider` + `useWebSocket` (typed `subscribe(type, handler)` returning an unsubscribe) and a `useWSEvent(type, handler)` hook.
- **NOT mounted anywhere by default** — nothing consumes the infrastructure out of the box; the generated README tells teams how to mount the provider in the app shell.

## LOCKED release contract

`ci/common` supplies POSIX `sh` release tooling; the selected host supplies pipeline files, `scripts/release/host.sh`, and adapter tests. `release.mk` is loaded by base's `-include *.mk`. Its `ci`, `release-test`, `release-preview`, `release`, `release-from-main` and `release-notify-test` targets call scripts explicitly with `sh`; `make test` also runs the shell suite inside Docker.

### Version assignment

A release version and its tag are `YYYY-MM-DD.N`, with no `v` prefix. The date is the release day in `RELEASE_TIMEZONE`, configured once in `scripts/release/config.sh` and defaulting to `UTC`. `N` is always written, starts at 1 and has no leading zero. Only a promotion with `RELEASE_PUBLISH=true` assigns a version; other promotions have an empty release version and build with `APP_VERSION=sha-<first 12 characters of SHA>`.

A commit receives one release tag for life and reuses it on redeploy or rollback. Assignment reads remote tags, reuses an existing tag for the commit, otherwise reuses its version from a finalised release record where the host supports that metadata, unless that version's tag proves it belongs to another commit. A new version takes one plus the highest daily release counter from remote tags and finalised record versions across environments. GitHub stores the version in the deployment description and payload; GitLab's deployment API offers neither field, so GitLab falls back to tags only. After a GitLab publication refusal that created no tag, the live image's counter can be reused by another commit or change on a later retry; once tagged, the version is stable. Failed or unhealthy runs create no release tag or finalised record and consume no counter.

For example, the first two production releases on 12 October 2026 are `2026-10-12.1` and `2026-10-12.2`. Rolling back on 13 October to the first commit reuses `2026-10-12.1`; a previously unreleased commit that day receives `2026-10-13.1`. Promoting a commit to a non-publishing environment such as `dev` assigns nothing and labels the build by commit. An environment added with `pimasi env add uat --publish` publishes, so its first promotion of a commit assigns the version and a later production promotion of that commit reuses it; no rule forces that order.

Tag parsing accepts date release tags and the hotfix shape `YYYY-MM-DD.N.P`, with positive release and patch counters and no leading zero. Tags sort numerically by date, `N` and `P`, so `.10` follows `.9`. A publishing hotfix takes its base release's date and `N`, then one plus the highest `P` already used for that base in tags and finalised record versions where supported. Hotfix tags do not consume daily release counters. One tag per commit, record-held version reuse, immutable tags and the GitLab metadata limitation apply to both shapes. Unrelated tags, including previous `v0.N.0` tags, remain untouched and are ignored for assignment.

Timezone validation fails before the gate or build if the IANA name cannot be resolved; it never falls back silently. GitLab installs `tzdata` in its Alpine job image, and GitHub's Ubuntu runner supplies timezone data. `RELEASE_NOW` optionally fixes the current epoch in seconds for script tests; ordinary runs leave it unset. Server and web images always carry their 12-character commit tag, and publishing builds additionally carry the release-version tag on the same image. `APP_VERSION` is the assigned release version when publishing; `GIT_SHA` and the server's environment defaults remain unchanged.

If publishing promotions in different environments race for one tag, an existing tag at another commit is refused. Promotion rereads remote state and retries once with a recomputed version, regenerating notes against the original destination baseline, rebuilding, redeploying, checking health and finalising a new record before publishing. The losing record still consumes its counter but cannot assign the other commit's tag on a later retry. A second collision leaves publication incomplete with a clear message and never moves a tag. A failed retry before recording reports failure with the attempted version; its summary acknowledges the first attempt's finalised record.

GitLab's job token creates tags through the releases API, which has no atomic tag-and-commit precondition. The adapter checks ownership before and after publication. Competing release creations preserve the first release's notes, but an external bare tag created between the checks can acquire the attempted notes before the conflict is detected and retried; the adapter never moves that tag. RELEASE.md documents this host limitation.

### Release branches, environment branches and hotfix admission

Work merges only to `main`, and a normal release uses its first-parent history. Release tooling keeps two further kinds of long-lived branch: `release/<version>` for each first-level version and `env/<name>` for each environment.

`RELEASE_BRANCH_PREFIX` (default `release/`) names release branches. After publication confirms the tag at the promoted commit, a first-level version `YYYY-MM-DD.N` gets `release/<version>` at that commit; a hotfix version `T.P` gets none. Any later publishing promotion of that version creates the branch when missing. An existing branch is never moved; hotfixes advance it, so the promotion warns only when the branch's first-parent line does not hold the tag. A refused branch write ends `succeeded, publication incomplete`, like a refused tag, and the next promotion of that version retries it. Release branches are kept, with no cleanup rule.

After the live record is finalised, every healthy promotion moves `env/<name>` to the promoted commit as a forced update, because rollbacks and hotfixes move it backwards or sideways. A refused move is a warning in a succeeded outcome; the record stays the source of truth for baselines and notes. Rejected, failed and skipped promotions move nothing.

A hotfix of T is a commit on `release/T`'s first-parent line strictly above T, where T is a first-level release tag (`YYYY-MM-DD.N`) whose commit is on main. The branch name gives the base; when a commit sits on the lines of several release branches, the release nearest to it on its own first-parent chain is its base. A commit that carries a hotfix tag `T.P` stays a hotfix of T, when T is a released tag on main and an ancestor, allowing redeploy and rollback after its branch is deleted or rewritten. Branches named `hotfix/` have no meaning. A commit off the release branch's first-parent line, such as one brought in by a merge, is refused, and a side commit merged into main is refused with a direction to promote the main commit that contains it. Admission, `notes.sh`, `classify.sh` and `version.sh` all take the base from `hotfix.sh`, so they apply this one rule. A hotfix may return to main by merge commit, squash or cherry-pick. Being contained by a merge does not change its hotfix identity, base or T.P version; tagged or branch-backed hotfixes remain promotable. A candidate on main's first-parent chain is always a normal release, including the merge commit itself.

The team decides what goes on the branch. The tool checks neither content nor hotfix lineage: trailers and patch comparison do not control admission, a rewritten release line is allowed, T need not be live, and a main candidate may omit a live fix. The hotfixes of one version normally form one line, so T.2 contains T.1. Bringing fixes back to main is the team's responsibility.

Only Maintainers push `release/*`, `env/*` and version tags and run releases, and only the pipeline moves `env/*`; no person pushes it by hand. Host protection enforces the pushes. On GitLab, `release/*` is a protected branch with push and merge allowed for Maintainers and no force push, `env/*` is a protected branch with push allowed for Maintainers and force push allowed, because rollbacks move it backwards, and the version tags are protected with creation allowed for Maintainers. The job token pushes as the person who started the pipeline, so that person must be a Maintainer; with job-token pushes on, a Maintainer who runs or retries a job on a branch they have not reviewed lends that branch's YAML their push rights. Deployment credentials stay protected variables, which reach pipelines on `main` and `release/*`, branches only Maintainers can push. On GitHub, `RELEASE_TOKEN` is a secret on each environment, never a repository or organisation secret, created by a Maintainer for this repository only with contents and workflows read and write (metadata read comes with it), or a GitHub App's token, and each environment accepts deployments only from `main`. Rules on `release/*`, `env/*` and the version tags block creation, update, force push and deletion; only the Maintain and Admin roles and the token's identity bypass them, and the default token is never exempt. Only Maintainers, Admins and the pipeline, through the environment-limited token, can then write those refs: a workflow on another branch can neither read the token nor write them with the default token. A workflow merged to `main` can attach to an environment and read its token. Protection does not stop a deployment. On GitLab Free, a run started below Maintainer deploys and writes its live record, then the host refuses its tag, release-branch and `env/*` writes: a publishing environment ends `succeeded, publication incomplete` and a non-publishing one succeeds with an environment-branch warning. On GitHub anyone with write access can still start **Release** on `main` for an admitted commit, which then writes as the token's identity. GitLab Premium protected environments and, where the plan offers them, GitHub required reviewers stop the deployment itself; the tooling checks no role, and a role check before anything builds is a recorded follow-up.

The scaffold and `add ci-<host>` record the answer to **Only Maintainers can release?** as `RELEASE_MAINTAINERS_ONLY=true` or `false` in `config.sh`; a `config.sh` without the key, such as one kept by a refresh from before, reads as off. When it is `true` and the promotion runs on GitHub Actions (`GITHUB_ACTIONS=true`), an empty `RELEASE_TOKEN` is rejected at admission, before anything builds, with a message naming RELEASE.md's "Maintainer-only releases" runbook; the check sees only that the token is set. On GitLab the switch changes no pipeline behaviour. The runbook gives both hosts' settings as web-interface steps; the CLI never applies host settings for the switch and calls neither `gh` nor `glab` for it.

Publishing assigns T.P with P one greater than the highest hotfix counter for T in tags and supported finalised record versions, whatever the lineage. A commit keeps one immutable release tag. Non-publishing environments assign nothing. Promotion carries admission's decision through the whole run: a hotfix keeps the base commit and tag that admission found for version assignment, notes, publication and the tag-race retry, even when its release branch is deleted or rewritten mid-run. A later promotion of a tagged hotfix finds its base through its T.P tag; an untagged hotfix whose branch no longer holds it is refused at admission, before anything builds, and notes for an admitted hotfix fail rather than fall back to normal-release notes. `RELEASE_AFTER`, gate, health, finalised records and publication still apply mechanically.

Admission needs the candidate, main, release tags, remote release branches and prerequisite live records; it does not read historical deployment commits. It fetches a missing prerequisite live commit by SHA before checking ancestry, refusing explicitly if the host cannot serve it, and fetches a missing release-branch tip before reading its line. Notes fetch a missing destination live commit by SHA. If fetching fails, the baseline is unknown, the notes say so and promotion continues. An untagged commit whose release branch was deleted loses its hotfix identity: it cannot be promoted, and notes treat it as an unrelated live commit.

Hotfix notes are titled as a hotfix of T. They list commits new relative to the live ancestor where possible; for unrelated live commits they say `moves <environment> from <what is live> to hotfix <T.P>` and list branch commits since T. Redeploy keeps its no-code-changes wording, and rollback lists removed commits, including a rollback between hotfixes. The next normal release uses T for ancestry and notes, with one short `Hotfix T.P was live` section listing the hotfix subjects, including after a merge commit. A hotfix commit that is an ancestor of the candidate, or a readable cherry-pick trailer naming an ancestor of the candidate strictly after the release base, marks a line `on main`; otherwise it says `confirm on main`. Trailers followed by sign-off lines remain readable. This is informational only, never a refusal. Unversioned hotfixes use base and SHA labels; rollback identifies hotfix removal.

Both hosts fetch full history including pushed release branches. Promotion gates and builds the exact candidate in a detached worktree using current main's tooling. On GitHub, tag, release and branch writes use `RELEASE_TOKEN`, an environment secret, when set; the Maintainer-only switch requires it, and otherwise projects using hotfixes or rollbacks should configure it with contents and workflow rights, because default-token writes may be refused when workflows differ from main's tip, leaving a healthy recorded promotion with incomplete publication or an environment-branch warning for a later retry. On GitLab, branch writes push to `origin` with the job token, as the person who started the pipeline, which needs the project setting allowing Git push requests, and every push carries `-o ci.skip`.

### Outcomes and records

`RELEASE_OUT` defaults to `.release`. Promotion writes shell-quoted `outcome.env` fields `outcome`, `stage`, `environment`, `sha`, `version`, `mode`, `base`, `health_url`, and `attempt`; values not yet known are empty. Companion artefacts are `notes.md`, `summary.md`, `images.env` and, when publishing, `publication.md`. The outcome vocabulary is **`succeeded`**, **`succeeded, publication incomplete`**, **`failed`**, **`rejected`**, and **`skipped`** for a superseded merge promotion. Stages are `admit`, `baseline`, `gate`, `build`, `deploy`, `health`, `record`, `publish`, and `done`; the main-tooling wrapper can also fail at `tooling`.

The baseline is the newest **finalised release record** for the environment, never a tag. GitHub requires `task: "release"`, the requested environment, and the latest deployment status `success`; creating a deployment without that successful status does not finalise it. GitLab requires a successful API-created deployment with `ref == sha`, no deployable job, and `tag == false`. Both adapters return deployment records newest first and paginate. GitHub preserves the server's descending creation order across pages and identifies records by their opaque GraphQL node id, without reading or sorting by the 32-bit database id; see the current [Deployment reference](https://docs.github.com/en/graphql/reference/deployments#deployment). GitHub stops the live-baseline read at the first finalised record and pages publication history with each deployment's latest status, avoiding one status request per historical record. Release jobs attach to their named host environment from the start. GitHub uses `environment.deployment: false` to avoid an automatic record at the pipeline SHA. GitLab uses `environment.action: start` to retain deployment approvals, so its page also shows an automatic pipeline-SHA deployment; the adapter ignores that record. GitLab's `action: access` avoids the automatic record and supplies scoped variables, but does not enforce deployment approvals. Failed admission, gate, build, deploy, health or record finalisation leaves the accepted baseline unchanged.

Only environments with `RELEASE_PUBLISH=true` publish a tag, release and release branch, and only after health and record finalisation; every healthy promotion, publishing or not, moves `env/<name>` right after the record. A tag is never moved. A release object, rather than an existing tag, marks publication complete. Failure or interruption during publication after recording produces `succeeded, publication incomplete`; re-promoting retries publication. On GitHub, notes use the record before that version's first finalised record in its original environment, so retries, rollback and another publishing environment retain its original deterministic notes. GitLab cannot recover that original publishing environment from deployment metadata, so an unpublished version promoted through another publishing environment uses that environment's first-promotion range. Existing release objects retain their notes on both hosts. Optional model notes affect summaries, not published release notes.

The default seam reports **images pushed and smoke-tested**, with no deploy target configured. A project replaces `deploy.sh` and sets `RELEASE_HEALTH_URL` before the summary claims a release to that target. Host pipelines serialise promotions with a `release-<environment>` lock and additionally serialise publishing promotions in the project-wide `release` group from assignment through publication, without cancelling active promotions. This prevents overlapping publishing environments reusing a record-held counter or assigning two lifetime tags to one commit across midnight. Non-publishing environments do not wait for the publication lock. GitHub uses `queue: max` on both locks so a slower older gate cannot discard a newer waiting commit; each queue holds at most 100 pending jobs. Direct script callers must provide equivalent environment and publishing serialisation for the whole promotion.

### Host adapter and environment seam

`host.sh` verbs are `marker-read <environment>` (SHA or empty), `marker-list <environment>` (newest-first JSON records including `sha` and `id`), `marker-list-all` (finalised record versions across environments on GitHub; an empty JSON array on GitLab), `marker-history` (newest-first finalised deployment SHAs, ids and environments on both hosts, without requiring version metadata), `marker-write <environment> <sha> <version>`, `tag-read <tag>` (commit SHA or empty), `tag-list` (remote JSON `[{tag,sha}]`), `release-exists <tag>`, `release-publish <tag> <sha> <notes-file>`, `branch-read <branch>` (SHA or empty), `branch-create <branch> <sha>` (creates the branch only when absent; 0 when it names the SHA, 4 when it names another commit, which stays untouched), `branch-move <branch> <sha>` (forced update, creating the branch when absent), `image-prefix`, `registry-login`, `summary <file>`, `title`, and `run-url`. `release-exists` returns 0 for present, 1 for absent, 2 for API or malformed-response errors; missing tags return empty output with 0. `release-publish` returns 4 for a tag owned by another SHA. Adapter validation/API errors use 2; Docker login and other external command failures remain non-zero. `RELEASE_HOST_ADAPTER` can override the adapter. GitHub uses the default token, with optional `RELEASE_TOKEN` for tag, release and branch rights, and writes branches through the git references API with a forced update for moves; GitLab uses the job token and requires GitLab 18.8 or later for single-tag reads, and its branch verbs read with `git ls-remote` and push to `origin` with `-o ci.skip`, create-only through an empty `--force-with-lease`. A tag read treats 404 as absent and 403 as an explicit permission error, never as an absent tag. Curl authentication and webhook URLs travel through restrictive temporary files or standard input, never secret-bearing process arguments.

Each `scripts/release/environments/<name>.env` is sourced shell configuration. These project-owned files are the source of truth; environments are not recorded in `pimasi.json`. Production is the given environment and the only one shipped. Projects create other environments with `pimasi env add`; names match `[a-z0-9][a-z0-9-]{0,31}`. Use `uat` for the conventional acceptance environment and `dev` for an independent development target.

Keys are `RELEASE_PUBLISH` (`true` enables tags, releases and release branches; default false), `RELEASE_ON_MERGE` (`true` enables promotion after the main push gate; absent by default), `RELEASE_HEALTH_URL` (optional API base URL without `/ping` or `/ready`; both probes share it, and empty uses the runner smoke check), `RELEASE_AFTER` (optional prerequisite environment), and public image build arguments: `VITE_API_URL`, `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_PUBLIC_WEB_URL`, `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, and `NEXT_PUBLIC_FIREBASE_APP_ID`. The shipped `production.env` enables publication and the local smoke check, with no on-merge key. `deploy.sh` receives exported `RELEASE_IMAGE_SERVER` and `RELEASE_IMAGE_WEB`; it must honour the requested SHA, and both health probes must pass before any record moves. GitHub passes the available secrets and vars contexts as JSON in `RELEASE_DEPLOY_SECRETS_JSON` and `RELEASE_DEPLOY_VARS_JSON` only to the promotion step; the deployment wrapper exports valid environment variable names for `deploy.sh` only, with secrets taking precedence, without printing them. The gate command uses a clean environment with operational variables only, excluding both JSON payloads and inherited deployment credentials. GitLab CI/CD variables reach the job and seam. New deployment credentials therefore need no workflow edit and survive refresh.

GitHub limits each serialised deployment context to 120 KiB (122880 UTF-8 bytes, including JSON keys, escaping and whitespace). The promotion step checks both contexts before running the release. A separate diagnostic without either payload reports a failed step launch when Linux rejects an environment string before the shell starts, around 128 KiB. Native run-script interpolation would print the JSON in the runner's script log, so the workflow retains environment transport with this explicit limit. Larger configuration must be fetched by `deploy.sh` from a manager or supplied by the application at startup. GitLab uses individual native CI/CD variables and has no combined JSON transport.

For publishing builds, `deploy.sh` also receives `RELEASE_IMAGE_SERVER_VERSION` and `RELEASE_IMAGE_WEB_VERSION` for the extra version tags on the same images; the default seam pushes those aliases as well as the commit references.

An absent or empty `RELEASE_AFTER` means independent: each environment can promote any admitted main commit or hotfix in any order, regardless of another environment's live SHA. Setting `RELEASE_AFTER=X` makes promotion sequential: the candidate must equal or be an ancestor of X's finalised live record, otherwise admission refuses before building. Relations must reference known environments and be acyclic. Every environment retains its own live record and notes baseline; promoting one never advances another, including when they are linked. Pipelines accept any environment file without a pipeline edit.

### Deploy on merge

Any environment may set `RELEASE_ON_MERGE=true`; new scaffolds ship only production with no such key. After a push to main passes the gate, each opted-in environment promotes that pipeline's SHA. `RELEASE_TRIGGER=merge`, matching `RELEASE_PIPELINE_SHA` and `RELEASE_GATED_SHA`, and matching non-empty `RELEASE_PIPELINE_ID` and `RELEASE_GATED_PIPELINE_ID` prove that this promotion already passed the gate in that pipeline. GitHub obtains that proof from its same-run job dependency and runner context. GitLab checks the claimed upstream pipeline against its API identity, project, SHA, main ref and push source before forwarding proof; it cannot prove the trigger relationship or completed gate from that response while the upstream gate waits. Missing, mismatched or unreadable proof runs the full gate. Manual promotions always gate again. Admission, `RELEASE_AFTER`, health, publication and environment-specific notes remain unchanged.

After acquiring its lock, a merge promotion fetches main and skips a superseded commit, or skips when a newer commit is already live. This prevents delayed old runs moving an environment backwards; intermediate commits may be skipped. If the newest main gate fails, the previous healthy record stays until another gate passes or a person promotes manually. A failed deployment leaves that environment's record unchanged, makes the pipeline red and releases its lock for the next attempt. Manual rollback remains supported.

### Where configuration lives

Build-time web settings are public values from the environment file, never secrets. At deploy time, the host environment page or any manager called by `deploy.sh` supplies what the target needs. At application start, the application or platform may fetch its own secrets, leaving the pipeline uninvolved. None of these storage locations is required or excluded, and combinations are supported. RELEASE.md gives examples for host variables, a manager call, keyless cloud login and runtime vault access. Projects whose application needs a vault that the runner cannot reach connect a real deployment target and set `RELEASE_HEALTH_URL`, because the default smoke check boots the server image on the runner.

### Environment commands

`pimasi env` also runs as `create-pimasi-app env` from a generated project root. All three commands require `pimasi.json` with `ci` set to `github` or `gitlab` and `scripts/release/environments/production.env` present. Otherwise they explain that `pimasi add ci-github` or `pimasi add ci-gitlab` comes first. They require no clean git tree and never change the manifest. Errors use add mode's style and exit 1; cancellation exits 0.

- `pimasi env list`: one row per file showing name, whether it is given (`production`), publication enabled, deployment on merge, `RELEASE_AFTER` or `independent`, whether a health URL is set, and host status (`exists`, `not yet created` or `unknown`).
- `pimasi env add <name> [--after <environment>] [--before <environment>] [--on-merge] [--publish] [--yes]`: copies the project's production file, setting `RELEASE_PUBLISH=false`, clearing `RELEASE_HEALTH_URL` and removing `RELEASE_AFTER` and inherited `RELEASE_ON_MERGE`. `--on-merge` writes `RELEASE_ON_MERGE=true`. `--publish` writes `RELEASE_PUBLISH=true`, so the environment creates versions; the documented example is `pimasi env add uat --publish`, and no rule forces it before production. Other values remain placeholders. With no relation the new environment is independent. `--after X` sets its `RELEASE_AFTER=X`; `--before Y` sets Y's `RELEASE_AFTER` to the new name. When Y already follows Z, the new environment follows Z and the command reports its insertion between Z and Y. The relation flags are mutually exclusive.
- `pimasi env remove <name> [--yes] [--keep-host]`: deletes the file and reports each follower re-linked to the removed environment's prerequisite, or made independent if it had none. A publishing environment can be removed locally only with `--keep-host`, preserving its host records. For other environments, after confirmation warning that host-side secrets and deployment history may go with the environment, it also deletes the host environment when reachable; `--yes` confirms and `--keep-host` skips host operations. Non-interactive host deletion requires `--yes`. An unavailable host does not prevent local removal, and the command reports that the host environment remains. Production cannot be removed.

Add names match `[a-z0-9][a-z0-9-]{0,31}`; adding `production`, overwriting an existing file, unknown relation targets and cycles are refused. Without a name, or without `--yes` on a terminal, add uses the existing prompt library for a name, the choice of independent, before or after an environment, deployment on merge, and "Create a version when deployed here?", which defaults to no unless `--publish` was given. `--yes` never prompts and requires a name. Reads and writes preserve comments, unknown keys and key order in existing files. Every created, changed or deleted file is printed, followed by the placeholders to edit, the `scripts/release/deploy.sh` target to connect and the exact promotion command for the manifest's host. On GitHub with `RELEASE_MAINTAINERS_ONLY=true` in `config.sh`, add also reminds that the new environment needs the `RELEASE_TOKEN` secret and deployments only from `main`, naming RELEASE.md's runbook; the reminder makes no host call.

Environment creation also uses an installed, signed-in `gh` or `glab` with the project's `origin` remote. The name is validated once and used verbatim. Existing host environments are preserved; missing tools, authentication, remote or rights produce one informational line and a successful local command. The first promotion attaches the environment and creates its host page even if deployment then fails. Host reads and mutations use the installed CLI, without new dependencies or HTTP code. GitLab removal also removes project variables scoped exactly to that name and force-stops the environment without running a stop job; wildcard, global and group variables remain. Partial host failures are reported without undoing the local removal. GitLab documents that deleting an environment deletes its deployments. GitHub documents removal of secrets and protection rules but makes no deployment-retention guarantee on its environment-deletion page; retention there remains unverified. Keeping publishing environments on the host preserves record-held allocation and publication history on either host.

Environment commands read literal assignments without executing shell code. Managed release settings must be single-line literals; quoted multiline values in unknown keys stay intact. Unsupported shell statements are refused before any writes. The command also refuses if the environment inventory or any file content changes while prompts are pending.

## The manifest (`pimasi.json`) and add mode

Every scaffold writes a `pimasi.json` at the project root — the machine-readable record of the selections: `{ name, cliVersion, frontend, database, design, cordova, workers, cache, rateLimit, websockets, ci }` (camelCase; 4-space JSON, matching the generated prettier config). It is the source of truth for add mode; projects without it (pre-0.2.0) cannot use `add`. `ci` is `github`, `gitlab`, or `none`; a missing key in a 0.2.0 manifest reads as `none`.

`pimasi add [feature…]` (also reachable as `create-pimasi-app add`, and auto-entered when the CLI runs with no arguments inside a directory containing `pimasi.json`) retrofits the four server axes — `workers`, `cache`, `rate-limit`, `websockets` — and one CI host, `ci-github` or `ci-gitlab`, onto an existing project. Adding a host when one is already selected is refused: switching hosts is a migration. Frontend/database/design/cordova are NOT addable: those are migrations, not adds. Scaffold-only flags are rejected in add mode; with no features named it prompts a multiselect of the currently-off features, including both host choices while ci is `none` (`--yes` requires naming them).

An add is **re-running composition for the delta**: it computes the fragment list old→new selections imply (including `server/redis` when the first redis-needing axis arrives, `websockets/<frontend>` per the manifest's frontend, and `ci/common` followed by `ci/<host>` for releases), applies them with the scaffold's replacement map built from the manifest name, then updates the generated files, bumps the root devDependency, and rewrites `pimasi.json` with the new axes + current `cliVersion` (a version mismatch with the scaffolding CLI is reported as info).

LOCKED conflict policy (files must never be silently clobbered):

- Requires a **clean git tree** after restoring missing root and server ignore files when the root `.gitignore` is absent, reporting each restoration (refuses on dirty or non-git; `--force` bypasses only for server features, never for CI add or refresh) so every add is reviewable with `git diff` and revertible. Only ignore files restored by this invocation are excluded from that check; unrelated changes still refuse the add.
- Fragment file absent on disk → write. Present and identical → skip. Present and different → compare against the **pristine render** of the same path from the current template or a stored released snapshot, using the project's replacements and selected fragment variant. A match makes the seam overwrite safe; a mismatch writes `<file>.new` beside it and reports. Published 0.2.0 snapshots cover the worker process config, email dispatch, rate-limit seam and release prerequisites.
- Pristine fragment and prerequisite comparisons use Prettier 3 with the file path and the project's root JSON `.prettierrc` when present, defaulting to `tabWidth: 4`. Only built-in formatting options are used; plugins and executable configuration are never loaded. This recognises published files after the generated pre-commit formatter has run while preserving syntax, strings and comments. The supported extensions are `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.json`, `.yml`, `.yaml`, and `.md`; unsupported files and parse failures compare byte for byte. Stored snapshots change only formatting from the published content.
- Fragment `package.json` partials merge **additively**: missing keys are added; existing keys always win and differing values are reported (an add never downgrades a user-bumped dependency).
- Generated files (`docker-compose.yml`, `.env.example`, the README `## Stack` block) compare against a re-render from the OLD selections, ignoring blank lines, trailing horizontal whitespace and CRLF line endings. The generated PostgreSQL healthcheck flow list also compares equally before and after Prettier wraps it across lines. Indentation, values and ordering must still match. A match replaces the generated content with the exact NEW render; otherwise emit `.new` (or print the new Stack block) and report. README matching covers only its generated Stack heading and list, preserving surrounding prose.

For a published 0.2.0 app, use `npx create-pimasi-app@latest add ci-<host>`: the explicit latest package avoids the locally installed 0.2.0 CLI, which lacks CI add mode. Apps already on a CLI with that feature keep using `npx pimasi add ci-<host>`.

Adding the first Redis-dependent server feature also supplies readiness prerequisites (registry, route, schema, selected database/Redis boot hooks and tests), using the same satisfied-content and untouched-or-`.new` rules. Readiness tests assert liveness without requiring release metadata from an older app's `/ping`; `ping.test.ts` owns version and commit assertions. Non-CI conflicts are reported under **Merge before building**.

## Conventions

- **Case by boundary**: `snake_case` ONLY for external contracts — API request/response fields, DB columns/document fields, queue/message payloads, JWT claims, env-var-shaped config. Everything internal is `camelCase`: local variables, function parameters, internal option objects, React state setters. camelCase fns; PascalCase types; UPPER_SNAKE module consts; kebab files; `let` in functions / `const` module-level.
- **Timestamped generated content** (migrations, ADRs, and anything similar) is named `YYYYMMDDHHMMSS-{kebab-description}` (14-digit, to the second) — e.g. `20260709120000-create-initial-indexes.ts`. Never sequential `0001` prefixes, never unix seconds.
- **HTTP + validation**: never `ajv`, `zod`, raw `fetch`, or `axios` — `@pimasi/utils` covers all of it (`lib/http`, `lib/json-schema`). This includes test helpers and client-side wrappers.
- British English; no AI-authored comments EVER (only humans write comments; preserve existing ones); ULID string ids everywhere (`ulid()`).
- **Template formatting**: fresh scaffolds pass Prettier 3 using their `.prettierrc` (`{"tabWidth": 4}`, double quotes by default), including generated YAML, JSON and Markdown. Format generated copies and port Markdown layout changes back while preserving literal placeholders in templates.
- **TypeScript + Prettier only, never ESLint** — no eslint configs, plugins, or deps in any workspace; tsc is the correctness gate, prettier the style gate. All source is TypeScript. Release tooling under `scripts/release/` is the explicit exception: POSIX `sh`, with POSIX awk for deterministic notes.
- Keep template dependency ranges at the LATEST published majors (verify with `npm view <pkg> version`); generated projects ship `make update-deps` (npm-check-updates across workspaces).
- Generated projects are **Docker-first and 100% dockerised** in dev: `make` targets wrap docker compose; ALL tests (every package, current and future) run inside the containers via `make test`; only type-check and formatters run on the host. README prose never hardcodes container names — `make` targets are the interface.
- AI agents working in generated projects must not use plan mode — they write plans to a gitignored `.scratch/` folder and validate with the user first (rule lives in the base README's AI section).
